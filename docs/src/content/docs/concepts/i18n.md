引擎的译文机制只有一条规则：**给一段原文，查表拿译文**。表的键就是原文本身。

原文是你在故事里写的那句话，所以译文表长这样：

```json
{
  "你好，{player.name}！": "Hello, {player.name}!",
  "接下来去哪里？": "Where to next?"
}
```

键里带着 `{player.name}` 不用管——插值发生在查表**之后**，译文里的占位符照常求值。

## 三种布局

译文表放哪由你决定，三种形态引擎都认：

| 布局 | 落盘路径 | 读出来是什么 |
| --- | --- | --- |
| 单文件 | `Lang/{lang}.json` | 一张表，按 `main.json` 对待 |
| 主表（文件夹平铺） | `Lang/{lang}/main.json` | 一张表，全局兜底 |
| 按故事镜像（文件夹分类） | `Lang/{lang}/<故事路径>.json` | 一个故事一张表，路径镜像 `Stories/` |

单文件适合词条不多的小工程。主表和单文件装的东西一样，区别是主表留出了加别的文件的位置。按故事镜像适合故事文件本来就分目录的工程——`Stories/chapter1/tavern.story` 的译文放 `Lang/en/chapter1/tavern.json`，路径去掉扩展名即可。平铺工程的「故事路径」就是故事 id。

供给层对 `Lang/{lang}/` 是**递归**收集的：主表那层能放几个文件，子目录里就能放几层。所以后两种其实是同一件事，文件夹分类只是把文件挪进了子目录。真正只有两种读法——目录，或者单文件。

三种形态摆在一起看：

```text
Stories/
  title/title_main.story
  chapter1/tavern.story

Resources/Lang/
  en.json                    ← 单文件：全部词条挤在一个文件里
  en/
    main.json                ← 文件夹平铺：一个语言一个目录，一张主表
    chapter1/
      tavern.json            ← 文件夹分类：按故事目录分文件
```

**目录和单文件同时存在时，目录赢。** 只要 `Lang/en/` 这个目录在，`Lang/en.json` 就不会被读。

## 合并规则

一次载入拿到多个文件，合并顺序是固定的：

1. `main.json` **最先**合并，它垫在底下当全局兜底。
2. 其余文件依次覆盖，同一个键后合并的赢。

引擎按**供给顺序**合并，原生供给会先把路径排一遍序，所以实际是路径序。单文件形态下你的文件被当成 `main.json`，没有覆盖者。

所以公共词条放 `main.json`，章节里要改口的放各自文件。

一个文件里只要有一个值不是字符串，**整个文件作废**——不会只跳过那一条。JSON 本身坏掉也一样，那个文件直接不算数，其余文件照常合并。

这条是供给层在做的：桌面壳和编辑器解析译文文件时，遇到坏 JSON、根不是对象、或者值里混了数字，就把整个文件丢掉。引擎只负责合并它拿到的条目，不解析磁盘——你自己写 `i18nPort` 时，这个判断得由你做。

## 接上供给端口

引擎不读文件系统，译文从 `i18nPort` 来。契约要的是两样东西：**一份文件清单**和**每个文件的条目**。列举哪些文件、怎么读、要不要解密，都是供给方的事——写死文件名就等于替供给方做了决定。

下面的实现假设宿主提供两个能力（列目录、读文本）。**这个接口就是契约说的供给侧**；换成 `ResourcePort.resolve()` 那条路也行，只要不绕过资源根去直拼 URL：

```ts
/** 宿主提供：列出资源根下某目录的文件。recursive 时含子目录；路径相对资源根，用 `/` 分隔 */
declare function listFiles(dir: string, options?: { recursive?: boolean }): Promise<string[]>;
/** 宿主提供：读一个文件的原始文本 */
declare function readText(path: string): Promise<string>;
```

一个译文表可能是坏 JSON、根不是对象、或者值里混了数字。三种都算**整个文件作废**，不会只跳过那一条：

```ts
function parseOverlay(raw: string): Record<string, string> | null {
  try {
    const parsed: unknown = JSON.parse(raw);
    if (typeof parsed !== "object" || parsed === null || Array.isArray(parsed)) return null;
    for (const value of Object.values(parsed)) {
      if (typeof value !== "string") return null;
    }
    return parsed as Record<string, string>;
  } catch {
    return null;
  }
}
```

端口本体。目录形态递归收集 `Lang/{lang}/` 下的全部 `.json`，目录里没有文件才降级去读单文件：

```ts
const overlayPort: I18nPort = {
  async loadOverlayFiles(lang) {
    const dir = `Lang/${lang}`;
    const inDir = (await listFiles(dir, { recursive: true })).filter((p) => p.endsWith(".json"));
    const paths = inDir.length > 0 ? inDir : [`Lang/${lang}.json`];

    const files: I18nOverlayFile[] = [];
    // 合并顺序决定同键谁赢，所以这里必须给出确定的顺序
    for (const path of paths.sort()) {
      const entries = parseOverlay(await readText(path));
      if (entries === null) continue;
      // path 是 overlay 根内的相对路径；单文件形态没有目录前缀，按 main.json 供给
      const rel = path.startsWith(`${dir}/`) ? path.slice(dir.length + 1) : "main.json";
      files.push({ path: rel, entries });
    }
    return files;
  },

  async listLanguages() {
    const seen = new Set<string>();
    const rest: string[] = [];
    for (const path of await listFiles("Lang")) {
      const lang = path.slice(path.lastIndexOf("/") + 1).replace(/\.json(\.enc)?$/, "");
      const key = lang.toLowerCase();
      if (lang === "" || key === "zh-cn" || seen.has(key)) continue;
      seen.add(key); // 大小写不敏感去重，写法取先出现的那个
      rest.push(lang);
    }
    return ["zh-CN", ...rest.sort()];
  },
};
```

几个容易写错的地方：

- **`path` 是 overlay 根内的相对路径**，`/` 分隔，不含 `Lang/{lang}/` 这一层。它不参与查表，但决定合并层级——`main.json` 不是随便起的文件名，引擎专门先找它垫底。单文件形态没有目录前缀，也按 `main.json` 供给，所以它享受同样的兜底待遇。
- **不要写死文件名**。写死 `chapter1.json` 这类具体路径，会让「按故事镜像」布局静默失效；工程只有主表时还会因为读不到文件而抛错，`loadOverlayFiles` 一 reject，`setLanguage` 就报 `i18n-overlay-failed`，**整个语言切不过去**。
- **两条路都读不到东西**（目录空、单文件也不存在），同样的失败路径。
- **列举要归供给方**。上面两个 `declare function` 是示意，真实宿主给你的是资源端口或文件源——用哪个都行，但别在页面里直拼 `/Lang/...`，那绕过了资源根。

`listLanguages()` 可选，引擎自己从不调用它，是留给语言选择器的。

模板自带的宿主**没有接**这个端口，所以 `Lang/` 目录里的译文不会被读，原文直接显示。参考宿主的桌面壳形态接了：扫 `Lang/`、按需读文件、遇到密文顺手解密，交到引擎手上时已经是条目了。浏览器形态现在没人给它接这条供给，密钥和格式知识都在原生层。纯前端那份实现也没有现成代码可抄，上面这段就是你自己接的路子。

## 语言列表从哪来

`listLanguages()` 是给你做语言选择器用的，**引擎自己从不调用它**——引擎只认 `setLanguage("en")` 传进来的那个语言码。

桌面壳的原生扫描认两种形态：`Lang/{lang}/` 目录和 `Lang/{lang}.json` 单文件。规则几条：

- 只看 `Lang/` 的**直接子项**。`Lang/en/zh-CN.json` 这种嵌进去的文件不会变成一种语言。
- 语言码就是目录名或文件名（去掉 `.json` / `.json.enc`）。
- 大小写不敏感去重，除默认语言外按码元序排。
- `zh-CN` 恒在列表里，排第一位。
- `Lang/` 目录不存在，或者扫不动——返回 `["zh-CN"]`，不报错。

编辑器那边不用这个扫描：它按**跨语言并集**收集译文键（`Lang/` 下所有 `.json` 的键合在一起）。因为「这个键在故事里找不到原文」跟具体哪个语言无关，只看单一语言会漏掉死键。代价是工作台认得的语言码比原生扫描宽松一点。

## 切换语言

```ts
await engine.setLanguage("en");
```

传空串表示回到默认语言（原文直出）。切换成功后写系统键 `__current_language`，宿主订阅它就能更新界面上的语言标记。启动前也能调，用来在标题画面选语言：

```ts
await engine.setLanguage("en");
engine.start();
```

载入失败时引擎保持原语言，发 `i18n-overlay-failed`：

```text
载入 en 译文 overlay 失败（保持原语言）：Failed to fetch
```

失败不会让故事停下来，也不会退回默认语言——之前那份译文表还在用。切换成功则是**整表重建**：旧表丢掉，新表按上面的合并规则重新拼一遍。

## 什么时候生效

切换语言后，**当前画面不会重画**。下一句 `say`、下一个菜单、下一次进入 `scene` 列时，取到的就是译文。

舞台元素不一样：元素的 `text` 在**装载时**就翻译好了，翻好的值进状态容器，跟着快照、存档、回溯一起走。所以：

- 切语言时，屏幕上已有的元素文字不变。
- 重新进入这个 `scene` 列，元素重新装载，文字变成新语言。
- 从存档回到这一刻，看到的是存档里那个语言的文字——存档里存的就是当时翻好的字符串。

这条是刻意的：元素文字是状态的一部分，回溯到英文进度时不该突然变成中文。

## 哪些文字会被翻

| 位置 | 翻译 |
| --- | --- |
| `say` 的正文 | 是 |
| `say` 的说话人名 | 是 |
| `menu` 的提示和选项文案 | 是 |
| `menu` 选项的目标列 | **否** |
| `input` 的提示 | 是 |
| `notify` 的文本 | 是 |
| `character` 的 `screen` | 否 |
| 元素的 `text` 属性 | 是（装载时） |
| 变量值、表达式结果 | 否 |
| `project.json` 的 `name` | 否 |

目标列名不翻译：它是列 id，不是给玩家看的文字。

`character` 的 `screen` 是角色的对话框模板注册名，值通常是 `bubble` 这类英文标识符——标识符不给玩家看，引擎不翻它；编辑器工具链把它算进翻译体检的比对面（见下文）。角色的显示名是 `name`，那个走 `say` 的说话人名。

## 原文直出

没接 `i18nPort`，或者调 `setLanguage("")`，引擎就不查表，原文直接送出去。这时 `Lang/` 目录完全不参与——不会去读，也不会报错。

默认语言由 `Resources/project.json` 的 `lang` 声明：

```json
{
  "lang": "zh-CN"
}
```

它只作为工程元数据，引擎不据此自动加载译文——加载时机由你调 `setLanguage()` 决定。

## 查表规则

- 命中就用译文，**包括空串译文**（想把某句在某个语言里藏掉，值写 `""`）。
- 没命中就用原文，不会报错也不会显示 key。
- 原文是空串时直接返回空串。

所以译文表漏了几条不影响运行，只是那几句还是原文。

## 加密译文

资源加密的工程里，译文文件也带 `.enc` 后缀：

```text
Resources/Lang/en/main.json.enc
```

引擎不知道这件事。`loadOverlayFiles` 交给它的是「路径 + 条目」，没有明密文字段——`Lang/en/main.json` 和 `Lang/en/main.json.enc` 对它来说是同一件事。解密在供给侧完成，跟资源、存档同一个口径，见[加密与平台供给](/concepts/encryption/)。

供给方要能解密，工程得先声明 `project.json` 的 `resourceEncryption`：

- 声明了 `resourceEncryption: true`，密文正常解密，解出来的条目照常参与合并。
- 没声明却出现密文，整次载入按失败处理——`setLanguage()` 报 `i18n-overlay-failed`，保持原语言。

浏览器形态的编辑器读回的是密文本身，JSON 解析必然失败，于是那个文件被跳过。这是有意的少报不误报：编辑器宁可不说，也不报一堆其实没问题的缺译。

## 编辑器里的本地化工作台

编辑器右栏的「本地化」面板管的就是 `Lang/**`。跑起来：

```bash
pnpm editor
```

默认开在 http://localhost:1425。面板顶部显示「原文 N 条」，下面每种语言一行。

得先「打开工程」——面板的数据来自已打开工程里扫到的译文键。工程里还没有任何 `Lang/` 文件时，它显示「尚未建立任何语言」，这不是报错，是空态。它自己也不碰磁盘：写盘走编辑器的保存通道，你在面板里点的每一步都不会背着你落文件。

### 覆盖率怎么算

一行里显示三样东西：**按字数加权的百分比**（最显眼）、状态标签、`已译/总数`。鼠标停在那个百分比上，提示里才有完整口径：

```text
按字数加权 62%（长句权重更大）· 按条数 88% · 原文 1240 字
```

两个数不一样，是因为条数比把一句长台词和一个两字词同等看待。译者体感是长句没翻更显眼，所以主显示用字数加权。权重取的是**原文长度**而不是译文长度——用译文长度会奖励「译得长」。

每种语言还有一个状态标签：

| 标签 | 含义 |
| --- | --- |
| 尚未开始 | 一条都没译 |
| 部分已译 | 译了一部分 |
| 已全部译出 | 原文全都有译文 |
| 无可译内容 | 工程里没抽到任何原文 |

「无可译内容」是显式判的空态，这时百分比位置显示的是「—」，不是 `NaN%`，也不是一个看起来很圆满的 100%——后两种都会让你以为翻译做完了。

有缺译时那一行会多出一个「缺译」按钮，点开是清单，每条后面一个「去译」——跳到该语言的译文表。译文表里有、原文里没有的键，在工作台底部汇总成「全部语言合计多译 N 条」。

### 新建一种语言

底部输入语言码（`en`、`zh-CN` 这种），选布局，点「生成骨架」。下拉里三项对应上面那张表：

```text
按主表（Lang/{lang}/main.json）
单文件（Lang/{lang}.json）
按故事镜像
```

默认选中第一项。生成的是**译文表骨架**：把工程里所有原文抽出来当键，值先占位。按故事镜像会把 `Stories/` 的目录结构照抄一份，每个故事一个文件。

占位策略有两种，默认是**原文占位**——没翻译时画面还是可读的，适合当翻译工作表用。另一种是空串占位，键在，值为 `""`，运行期命中即隐句，适合你想让未译内容干脆不显示的场景。编辑器面板走默认的原文占位。

生成是**增量**的：该语言已经存在的译文原样保留（包括你故意留的空串），只补新键。语言已经建过时，它会先问你一句：「仍要生成骨架吗？已有译文会被保留（增量模式），但可能覆盖同名文件。」

语言码必须是一段安全的文件名——它要当目录名用，规则和故事文件名同一套。带 `/`、写成 `..`、以点开头都会被拒，报错原文：

```text
语言码不合法：../x（须为单段安全文件名）
```

生成完会提示「已生成 en 骨架：3 个文件」，然后重新枚举工程，诊断面板和工作台的数字跟着更新。写盘中途出错会弹「生成失败：…」——但已经写下去的文件不回滚，你得自己看一眼哪几个落地了。

### 译文表怎么编辑

点语言码（或某条缺译后面的「去译」）进译文表：左边键、右边值，可增删改行。

- **输入即暂存，保存按钮显式**。不会边打字边写盘。
- 空译文显示灰色占位「未翻译」，而不是一片空白——空白分不清「还没译」和「故意留空」，而这两件事在运行期行为完全不同。
- 新增行先问你键名再插行，提示「请输入原文键（须与原文一致；运行期按此键查译文）。」
- 删行要二次确认，因为删掉就没了，译文表不带备份。

## 翻译体检

编辑器诊断面板里跟译文有关的两条，都是警告级：

**未使用的译文键**。译文表里有这个键，但故事里找不到对应原文：

```text
未使用的译文键：你好（say / menu / input / notify 四个翻译面均未命中原文——该键运行期不会生效；若这段文字只用于元素文本或宿主界面，本条可忽略）
```

消息里写的是「四个翻译面」，实际参与比对的是五个（还有 `character` 的 `screen`）加上元素 `text`。这条消息的文案还没跟上。命中它通常是改台词时忘了同步译文表。

**缺译文**。原文没有任何一种语言的 overlay 命中：

```text
原文未有任何译文：欢迎回来（所有语言的 overlay 均未命中——运行期回退原文；专有名词等有意保留原文的可忽略）
```

第二条只在工程**确实有** overlay 键时才提醒。一个纯中文工程不会被它刷屏。

同质诊断会淹掉异质诊断——三十多条「未使用的译文键」里埋着两条真错误，很难发现。所以诊断面板按类型分组：错误组永远在最上面且不折叠，警告组条数大于 1 时默认折叠。工作台底部的「全部语言合计多译 N 条」和诊断面板里的「未使用的译文键」是同一份数据。
