---

发版的入口是一条命令。它会算出版本号、把八份清单改成同一个号、跑完门禁、提交、打注记标签，然后把分支与标签一起推上去。

```bash
pnpm release --bump patch
```

推上去之后，标签触发发版工作流：它复核门禁、打包自检、用 OIDC 换证发布到 registry、再按提交历史生成 Release。**本地这一步不发布 npm**——两处各发一次，registry 上的内容与标签就对不上了。

## 版本号怎么给

三档递增，或用 `--version` 指定确切版本：

```bash
pnpm release --bump patch          # 0.1.5 → 0.1.6
pnpm release --bump minor          # 0.1.5 → 0.2.0
pnpm release --bump major          # 0.1.5 → 1.0.0
pnpm release --version 0.2.0-rc.1  # 直接指定，含预发布后缀
```

当前版本带预发布后缀时，三档都只清后缀、不再涨一档：`0.2.0-rc.1` 的补丁位就是 `0.2.0` 本身——预发布是某个正式版本的预览，正式化不该再多走一格。

预发布后缀只认三段的写法：`0.2.0-rc.1` 合法，`0.2.0.rc.1` 不合法（语义化版本的主次修订是三个数字位）。带 `+构建元数据` 的版本会被拦下——npm 发布时会把 `+` 之后静默裁掉，registry 上的号、标签、清单里的号当场对不上。

## 两种标签名的区别

正式版发 `latest`，预发布版发它后缀的第一段：

| 版本            | dist-tag | 装到它的方式             |
| --------------- | -------- | ------------------------ |
| `1.2.3`         | `latest` | `npm install <包>`       |
| `1.2.3-rc.1`    | `rc`     | `npm install <包>@rc`    |
| `1.2.3-alpha.1` | `alpha`  | `npm install <包>@alpha` |

用后缀第一段而不是统一写 `next`，是为了让 rc 与 alpha 这几种预览在 registry 上互不覆盖。

## 命令会拦下的情况

发版脚本在动手之前先看几件事，任一不满足就停：

- **当前不在 `main`**：标签会指向 main 上的提交，在别的分支上打标签，release 页会指错地方。
- **工作区不干净**：改清单之后的提交会把未提交的改动一起带走，混进一次发版的提交里。
- **版本号非法**：见上一节。
- **标签已存在**（本地或远端）：同一个版本不能对应两个提交，换一个号。

门禁排在提交之前：类型检查、代码风格、单元测试、运行期可达图检查任一道不过，就不提交也不打标签。标签必须指向一个自身通过的提交——先提交再检查的话，一旦失败就得用补丁提交去追，而标签可能已经推出去了。

## 只预览、不落地

```bash
pnpm release --bump patch --dry-run   # 打印将要改的清单数量，不写文件、不跑门禁
pnpm release --bump patch --no-push   # 做到本地提交与打标签为止
```

`--dry-run` 不检查工作区是否干净：预览本身不改任何文件，脏工作区不该拦住看一眼。

`--no-push` 的典型用途是先把提交与标签准备好，等网络或时机合适再手动推：

```bash
git push origin main && git push origin v0.1.6
```

## 发布之后

推送标签后几分钟内可以核这三处：

```bash
npm view <包名>@<版本> version          # registry 上有这个版本
npm view <包名> dist-tags              # latest 或 rc / alpha 指向它
```

Release 页由工作流自动建出，正文取自提交历史里那一段的「新增 / 优化 / 修复 / 其他变更」分节。因此**提交信息写成分节格式**是发版说明质量的前提，写成一行的提交只会在说明里留下那一行。

发布是幂等的：工作流逐包先问 registry「这个版本在了吗」，在了就跳过。中途某个包失败时，原样重跑一次不会因为「版本已存在」整体失败。
