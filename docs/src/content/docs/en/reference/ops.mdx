There are 65 built-in ops, grouped by purpose into nine domains with one page each. This page is the entry point: find an op by name, follow it through to its signature, arguments and gotchas.

## Two forms

Every op has two forms projecting onto the same command:

- **Text form** — written in `.story` files, one op per line, indentation for block bodies.
- **JSON v1** — written in `.json` files, one op per object.

A project can mix both; the engine decides which parser to use from the file's contents. The signatures on the domain pages give the text form, and the argument tables list JSON field names — the two line up one to one, and the field name is exactly the key you write as `key=` in text form.

```text
say "It's eleven at night, and it's still raining." speaker="A-Lan"
```

```json
{ "op": "say", "text": "It's eleven at night, and it's still raining.", "speaker": "A-Lan" }
```

## Wait points

Eight ops create wait points. Execution stops at them until the player acts:

| Op | Waiting state | How it clears |
| --- | --- | --- |
| `say` | `dialog` | The player clicks or presses a key |
| `menu` | `menu` | The player selects an option |
| `input` | `input` | The host supplies the input |
| `wait` | `wait` | The timer expires; with `skipable`, a click also clears it |
| `pause` | `wait` | The timer expires. `pause` is never skippable |
| `cutscene` | `video` | Playback finishes; with `skipable`, a click also clears it |
| `minigame` | `minigame` | The host supplies the result |
| `interaction` | `interaction` | The host supplies the result |

The other 57 do not stop; they run and move on. `video` is the one people get wrong — playback starts and execution continues. Use `cutscene` when you need it to finish first.

A wait point is also a checkpoint coordinate. Rollback lands on the previous wait point and loading lands on one too, which makes wait points save points.

## Built-ins cannot be overridden

An extension op that shares a built-in's name throws at registration time and the whole project fails to load:

```text
扩展 demo 的 op「say」与内建 op 冲突（内建不可覆盖）
```

Lookup order is built-in → extension → unknown. A custom op cannot shadow a built-in; writing one only makes the project fail to open, it never quietly takes over. Extension ops create no wait points either — a successful execution just steps forward.

See [Extending the Engine](/en/concepts/extensions/) for the details.
