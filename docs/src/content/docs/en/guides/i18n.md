---

The mechanism behind multilingual stories is one rule: take a source string, look it up in a table, get the translation. The tables live in `Resources/Lang/`; keys are source strings, values are translations.

```json
{
  "你好，{player.name}！": "Hello, {player.name}!",
  "接下来去哪里？": "Where to next?"
}
```

The key carries `{player.name}` — interpolation happens **after** the lookup, so translations can reuse the same placeholders and both sides share the same variables.

The mechanics of the port, language enumeration and encryption are covered in [Multilingual Stories](/en/concepts/i18n/). This page walks through the workflow in order.

## Pick a layout

Three layouts, differing only in where files land:

| Layout           | On-disk path                    | When to pick it                      |
| ---------------- | ------------------------------- | ------------------------------------ |
| Single file      | `Lang/{lang}.json`              | Few entries; one file fits them      |
| Main table       | `Lang/{lang}/main.json`         | You want room for more files later   |
| Per-story mirror | `Lang/{lang}/<story path>.json` | Your stories already live in folders |

The per-story mirror path aligns with `Stories/`, minus the extension: translations for `Stories/chapter1/tavern.story` go to `Lang/en/chapter1/tavern.json`. Skeleton generation computes paths by this rule; follow it when writing files by hand too.

The main table and the per-story mirror can be mixed: `main.json` is the global fallback layer, merged first; the remaining files override it in path order, and for the same key the later merge wins. So put sentences reused across chapters in `main.json` and translate them once, and keep chapter-specific lines in the chapter files.

The single file is the fallback shape when no directory exists; it cannot be mixed with the other two. When both `Lang/en/` and `Lang/en.json` exist, the directory wins — the single file is not read.

Switching layouts does not change the key set: the three layouts only differ in where keys are placed; the extracted keys are the same set. Migrating from a single file to a directory (or back) just means moving existing translations by key — no entries appear or disappear. The CLI check verifies that the three layouts produce identical key sets (see below).

Every value in a translation file must be a string. One non-string value **invalidates the whole file** (the file is skipped, not the offending line); the source text shows as usual, which looks a lot like "nothing happened".

## Generate a skeleton

A skeleton is a translation table with every translatable source string from the stories as keys and placeholder values. Copying keys by hand risks a single wrong punctuation mark making a lookup miss forever, so generate them with a tool. The editor panel flow is below; the command-line equivalent is `lingfan-i18n skeleton` further down:

1. Run `pnpm editor` at the repository root and open http://localhost:1425 .
2. Use the toolbar's "Open project…" to select the project root (the level containing `Resources/`) and grant edit permission.
3. Switch the right column to "Localization"; at the bottom of the panel, "New language": enter the language code, pick a layout, click "Generate skeleton".

The three layout options are the table above: `Main table (Lang/{lang}/main.json)`, `Single file (Lang/{lang}.json)`, `Per-story mirror`, with the first as default. The language code must be a single safe filename segment — `en`, `zh-CN`, `pt-BR` all work; `../x` is rejected:

```text
语言码不合法：../x（须为单段安全文件名）
```

Keys are computed per story: in the mirror layout, keys from `Stories/chapter1/tavern.story` land in `Lang/en/chapter1/tavern.json`; the main-table and single-file layouts merge all stories' keys into one file. Generation reports the file count, then the project is re-enumerated and the new language appears in the panel immediately:

```text
已生成 en 骨架：3 个文件
```

When the language already exists you are asked first: "仍要生成骨架吗？已有译文会被保留（增量模式），但可能覆盖同名文件。" Incremental mode keeps the values you already translated, including **deliberately empty strings**. So regenerating is safe; use it to top up when keys change.

Skeleton values default to the source text, making the file a translation worksheet: just replace values with translations. The alternative is empty-string placeholders — keys are still created, values written as `""`; a runtime hit applies immediately and that line simply does not display in that language. The editor panel uses the default source-text placeholders; for empty placeholders, clear the values yourself.

Writing goes through the editor's write-back channel, which needs a project opened with write access. A project opened as a read-only snapshot reports:

```text
生成骨架需要写回能力。请先「打开工程」并授予编辑权限。
```

## Translate and save

Click a language code in the panel, or "Translate" from the missing list, to enter the translation table: source keys on the left, translations on the right; you can add, delete and edit rows.

Typing stages changes; **saving is an explicit action** — only clicking save after the dirty marker appears writes to disk. Empty translations render as a grey placeholder rather than blank, because blank cannot distinguish "not translated yet" from "deliberately empty", and those two behave completely differently at runtime.

Adding a row asks for the key first: "请输入原文键（须与原文一致；运行期按此键查译文）。" The key must match the story text character for character; one extra space means a permanent miss. Deleting a row asks for confirmation; the translation table keeps no backup.

## Watch progress

The top of the panel shows coverage: the main figure is weighted by **character count**; hovering reveals the per-entry percentage and the total source character count.

The per-entry ratio overstates completion — untranslated entries tend to be short words, so missing two out of dozens still reads as 98%, yet the line the player reads is in the source language. The weighted figure weights by source length, so an untranslated long sentence costs more, closer to a translator's intuition.

There are four states: `无可译内容` (nothing translatable), `尚未开始` (not started), `部分已译` (partially translated), `已全部译出` (fully translated). Next to it is `translated/total`; click "Missing" to expand the list, each entry followed by a "Translate" link that jumps to the table and locates that row.

## Run the translation check-up

After translating, run the diagnostics panel; several warnings relate to translations. The command line runs the same reconciliation and can serve as a CI gate (see `lingfan-i18n` below).

Missing translation:

```text
原文未有任何译文：欢迎回来（所有语言的 overlay 均未命中——运行期回退原文；专有名词等有意保留原文的可忽略）
```

This only fires when the project actually has translation keys. A project with no `Lang/` at all is not reported — such a project is meant to display source text directly.

Orphaned translation:

```text
未使用的译文键：欢迎回来（say / menu / input / notify 四个翻译面均未命中原文——该键运行期不会生效；若这段文字只用于元素文本或宿主界面，本条可忽略）
```

Orphans usually come from editing the source without editing the translation: the line in the story changed, and the old key became an orphan that never matches. The four command surfaces named in the message are shorthand: the comparison actually covers five command surfaces (`say` text and speaker, `menu`, `input`, `notify`, `character`'s `screen`), plus element `text` and the static-string keys wrapped in `t()` in host source.

The workbench footer's "全部语言合计多译 N 条" and the diagnostics panel's "未使用的译文键" are the same data.

Two more warnings concern the host and file placement:

- **Unmarked host strings**: literals in host source that contain Chinese but are not wrapped in `t()`. They never enter the key set and will never be translated; the diagnostic gives file, line and column — wrap the player-facing strings.
- **Layout conflict**: the same key appears in multiple files of one language with different values. Merging is last-write-wins, so a conflict means one translation is silently shadowed — deduplicate the key down to one place.

## Command-line toolchain: lingfan-i18n

The editor panel suits translating while watching; batch generation, reconciliation and CI gates go through the command line. Template projects already carry `@lingfan-engine/editor` in dev dependencies, so run directly at the project root:

```bash
pnpm exec lingfan-i18n <subcommand> [project-root] [options]
```

The project root resolves through three levels: positional argument > environment variable `DSH_I18N_ROOT` > current directory. Four subcommands:

| Subcommand | What it does                                                         | Writes to disk |
| ---------- | -------------------------------------------------------------------- | -------------- |
| `scan`     | Key inventory: story keys + host keys + dynamic calls                | No             |
| `skeleton` | Generate/update the translation skeleton for one language            | Yes            |
| `report`   | Reconciliation report for one language (missing, orphaned, coverage) | No             |
| `check`    | Same reconciliation as report + exit-code gate                       | No             |

The story side collects keys from **compiled artifacts** only (it does not scan story source); the host side scans source. So compile the stories first (see [TS story source](/en/advanced/ts-story-source/)) to make sure the keys are current.

### scan: see what keys exist

```bash
pnpm exec lingfan-i18n scan
```

```text
故事键 42 条（3 个编译产物）
宿主键 7 条（5 个源文件）
动态调用点 0 处（登记调用首参均为字面量）
```

`t()` calls whose first argument is not a literal cannot be collected; they are listed separately as a reminder:

```text
动态调用点 1 处（首参非字面量，无法静态收键）：
- src/host/toolbar.ts:18:12 t()
```

Host literals containing Chinese but not wrapped in `t()` are also reported here (unmarked host strings). By default only literals containing Chinese are collected; `--all` collects the rest too.

### skeleton: generate the skeleton

```bash
pnpm exec lingfan-i18n skeleton --lang=en --layout=main
```

`--lang` is required; `--layout` takes `single` / `main` / `per-story`, defaulting to `per-story`. The placeholder policy is `--placeholder=original|empty`, defaulting to `original` (source-text placeholders, usable as a translation worksheet); `empty` writes empty strings, hiding the line at runtime on a hit.

Generation is idempotent and incremental: existing translations are kept as-is and only new keys are added; files whose content matches disk are not touched:

```text
骨架 3 个文件（写入 2，未变 1）
```

`--prune` also deletes orphan keys with no source — a destructive operation, off by default; when enabled it lists every deleted key. Orphan files outside the plan are only diagnosed explicitly, never actually deleted.

### report and check: reconciliation and the gate

```bash
pnpm exec lingfan-i18n report --lang=en
pnpm exec lingfan-i18n check --fail-on=any
```

`report` requires `--lang` and prints that language's missing translations, orphan keys, unmarked strings and coverage:

```text
[en] 覆盖率 88%（字数加权 62%，52/60 键）
```

`check` reconciles **every language** by default (when `Lang/` is empty or absent it reports "未发现任何 overlay"), and at the end verifies that the three layouts produce identical key sets — layouts only change file organization, not the key set, so this check reports only and never blocks:

```text
三布局键集合一致性：通过（只报告，不阻断）
check 通过
```

`--fail-on` decides what counts as failure: `missing` (missing translations, the default), `unused` (orphan keys), `any` (any of missing, orphaned, unmarked static strings). On failure it prints `check 失败（fail-on=…）` and exits non-zero, ready to wire into CI.

Exit-code convention: **0** success; **1** check failure or I/O failure; **2** argument error.

### Registering other translation function names: --functions

The scanner recognizes `t()` by default. If the host aliases the translation function (say `tr`), register it with `--functions`, comma-separated:

```bash
pnpm exec lingfan-i18n scan --functions=t,tr
```

The value resolves through three levels: command-line `--functions` > the project manifest `project.json`'s `i18n.functions` > default `["t"]`. Manifest form:

```json
{
  "i18n": {
    "functions": ["t", "tr"]
  }
}
```

The manifest section must be an object and `functions` must be an array of strings; an empty list or an empty function name is rejected — better an error than a silent scan gap.

Every subcommand supports `--json`, emitting machine-readable results for scripts.

## Which strings enter the table

When writing stories, use this table to decide what gets translated:

| Location                             | In the table |
| ------------------------------------ | ------------ |
| `say` text                           | Yes          |
| `say` speaker name                   | Yes          |
| `menu` prompt and option labels      | Yes          |
| `input` prompt and option labels     | Yes          |
| `notify` text                        | Yes          |
| `character`'s `screen`               | Yes          |
| Element `text`                       | Yes          |
| Host static strings wrapped in `t()` | Yes          |
| `menu` option target column          | No           |
| Variable values, expression results  | No           |
| `project.json`'s `name`              | No           |

`character`'s `screen` is the registration name of the character's dialogue-box template, usually an English identifier like `bubble`, so it rarely needs translating; but it is a string field, so it is in the table. The character's display name is `name`, which goes through `say`'s speaker name.

The target column is not in the table — it is a column id. Neither is an `input` candidate's `value` — that is the raw value written into a variable. Variable values and expression results are likewise excluded — they are data, not copy. Names the player types are excluded too.

## Switching languages

```ts
await engine.setLanguage("en");
```

It can be called before startup too — that is what a title-screen language picker uses.

After a successful switch, **the current screen re-translates immediately**: the `say` line on display, menu and input prompts and options, element text on screen, and lines already scrolled in the NVL all switch to the new language. State stores source text; translations are derived at read time from the current table, so there is no waiting for the next line and no re-entering the scene.

Snapshots and saves store source text too. What language a loaded save displays in depends on the language setting at load time; rolling back to any checkpoint derives the screen and history panel in the current language as well. Saves from older versions stored translations; on load the engine skips table lookup for fields suspected to be translations, avoiding double mistranslation — the save format has not changed and no migration is needed.

On failure the engine **keeps the current language**, leaves the table untouched, and emits `i18n-overlay-failed`:

```text
载入 en 译文 overlay 失败（保持原语言）：Failed to fetch
```

Passing an empty string returns to direct source display — `project.json`'s `lang` is project metadata only; the engine does not auto-load its translations from it (see [Multilingual Stories](/en/concepts/i18n/)).

## The language picker

The language list comes from the host. The template host does no runtime scanning: the manifest is produced at build time by scanning `Resources/Lang/` (the `virtual:lang-list` virtual module, exported through `src/langs/`); at runtime files are fetched by the list, so adding a language directory needs no manifest edit. The facade's `availableLangs` always contains the default language and fills in asynchronously when a supply port is wired; if fetching the list fails it keeps the default without erroring.

The template already wires this supply: both the browser and desktop shells use Web fetch — `Lang/` is a static asset and the desktop shell's WebView fetches it the same way; the mini-program shell uses an injectable HTTP client. Run the template as-is and `Lang/` participates directly, with a language picker on the page.

Two details when wiring your own picker:

- **The default-language option's `value` must be the empty string**. The engine treats the empty string as "default language, direct source display"; filling in a code like `zh-CN` counts as a real switch, and without a matching table it is treated as a failure. The option's display label can be the language code itself — language names are data, not translated.
- After a successful switch, repaint the host's own static strings (toolbar buttons, save labels — literals wrapped in `t()`) and remount panels that cached copy (preferences, history). The template's wiring lives in `src/host/i18n.ts` and can be used as a reference.

The reference host shows the picker only when the list has more than one entry — showing it for a single language is pointless. The port contract and facade API are in [Multilingual Stories](/en/concepts/i18n/).

## Encrypted translations

`Lang/en/main.json.enc` is collected alongside `Lang/en/main.json`, decrypted at collection time, then merged by the same rules. For ciphertext to be decryptable, `project.json` must declare `resourceEncryption`; ciphertext without a declaration fails the whole load and keeps the current language.

## A few lookup rules

- A hit uses the translation, and **an empty-string translation is a hit too** — writing `""` means "display nothing", not "use the source".
- A miss uses the source.
- If the source itself is the empty string, the empty string is returned without a lookup.

## A complete example

Per-story mirror plus a main-table fallback; the project looks like this:

```text
Resources/
  project.json
  Stories/
    chapter1/tavern.story
  Lang/en/
    main.json                sentences reused across chapters
    chapter1/tavern.json     mirrors Stories/chapter1/tavern.story
```

`main.json`:

```json
{
  "要继续吗？": "Do you want to continue?"
}
```

`chapter1/tavern.json`:

```json
{
  "先问一句：你叫什么名字？": "First, what should I call you?",
  "你好，{player.name}！": "Hello, {player.name}!",
  "接下来去哪里？": "Where to next?",
  "去码头": "Head to the docks",
  "回家": "Go home"
}
```

The story `Stories/chapter1/tavern.story`:

```text
label start:
  input "先问一句：你叫什么名字？" store="player.name"
  say "你好，{player.name}！"
  menu "接下来去哪里？"
    "去码头" -> dock
    "回家" -> home
```

The `input` prompt and the `say` text both go through the table. The name the player types does not — it is data. The `menu` option labels go through the table; the target columns `dock` / `home` do not.

The keys in `chapter1/tavern.json` can be seeded by skeleton generation. The `main.json` one must be written by hand: the mirror layout splits files per story and will not merge the same source line from different stories for you; sentences reused across chapters go here so they are translated once.
