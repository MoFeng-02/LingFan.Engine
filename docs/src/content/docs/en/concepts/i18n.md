title: Multilingual Stories
description: Translations are keyed by the original text and can live in a single file, a main table, or per-story mirrors; state stores originals, switching language re-translates immediately, old saves degrade gracefully — plus merge order, language enumeration, the host facade, and encrypted translations.
---

The engine's translation mechanism has exactly one rule: **given a piece of original text, look it up in a table**. The keys of that table are the original text itself.

The original is the sentence you wrote in the story, so a translation table looks like this:

```json
{
  "你好，{player.name}！": "Hello, {player.name}!",
  "接下来去哪里？": "Where to next?"
}
```

Don't worry about the `{player.name}` inside the key — interpolation happens **after** the lookup, and placeholders in the translation are evaluated as usual.

## Three layouts

Where the tables live is up to you; the engine accepts all three shapes:

| Layout            | Path on disk                    | What gets read                            |
| ----------------- | ------------------------------- | ----------------------------------------- |
| Single file       | `Lang/{lang}.json`              | One table, treated as `main.json`         |
| Main table (flat) | `Lang/{lang}/main.json`         | One table, the global fallback            |
| Per-story mirror  | `Lang/{lang}/<story path>.json` | One table per story, mirroring `Stories/` |

A single file suits small projects with few entries. The main table holds the same content as a single file; the difference is that it leaves room for additional files. The per-story mirror suits projects whose story files already live in directories — the translation of `Stories/chapter1/tavern.story` goes into `Lang/en/chapter1/tavern.json`, just drop the extension. For flat projects the "story path" is simply the story id.

The supply layer collects `Lang/{lang}/` **recursively**: however many files the main-table level can hold, subdirectories can nest just as deep. So the latter two are really the same thing — folder classification just moves files into subdirectories. There are truly only two ways to read: a directory, or a single file.

All three shapes side by side:

```text
Stories/
  demo/demo_intro.story
  chapter1/tavern.story

Resources/Lang/
  en.json                    ← single file: every entry in one file
  en/
    main.json                ← flat folder: one directory per language, one main table
    chapter1/
      tavern.json            ← classified folders: one file per story directory
```

**When a directory and a single file both exist, the directory wins.** As long as `Lang/en/` exists, `Lang/en.json` is never read.

## Merge rules

When one load brings in several files, the merge order is fixed:

1. `main.json` merges **first**, sitting underneath as the global fallback.
2. The remaining files overwrite in turn; for the same key, the later merge wins.

The engine merges in **supply order**; the native supply sorts paths first, so in practice it is path order. In the single-file shape your file is treated as `main.json` and has no overriders.

So put shared entries in `main.json`, and chapter-specific rewordings in their own files.

If even one value in a file is not a string, **the whole file is discarded** — not just that entry. The same goes for broken JSON itself: that file simply doesn't count, and the rest merge as usual.

This is the supply layer's job: when the desktop shell, the Web fetch adapter, or the editor parses translation files, broken JSON, a non-object root, or a number mixed into the values makes it drop the entire file. The engine only merges the entries it receives and never parses disk — when you write your own `i18nPort`, that check is yours to make.

## Wiring up the supply port

The engine does not read the file system; translations come from `i18nPort`. The contract asks for two things: **a file list** and **the entries of each file**. Which files to enumerate, how to read them, whether to decrypt — all of that belongs to the supplier. Hard-coding file names would make that decision for the supplier.

Common platforms don't need hand-written code: `@lingfan-engine/adapters` ships three ready-made implementations — `createFetchI18nPort` (browser fetch, with the language list produced by a build-time scan), `createHttpI18nPort` (an injectable HTTP client, for environments without a global fetch such as mini programs), and `createTauriI18nPort` (native desktop supply: directory scanning, file reads, and decryption all happen on the native side). The hand-written implementation below shows the shape of the contract itself; follow it when building a custom supply.

The hand-written version assumes the host provides two capabilities (list a directory, read text). **This interface is the supply side the contract talks about**; going through `ResourcePort.resolve()` works too, as long as you don't bypass the resource root by building URLs directly:

```ts
/** Provided by the host: list files under a directory of the resource root. Recursive includes subdirectories; paths are relative to the resource root, separated by `/` */
declare function listFiles(
  dir: string,
  options?: { recursive?: boolean },
): Promise<string[]>;
/** Provided by the host: read the raw text of one file */
declare function readText(path: string): Promise<string>;
```

A translation table may be broken JSON, have a non-object root, or contain a number among its values. All three count as **the whole file discarded**, never just one entry:

```ts
function parseOverlay(raw: string): Record<string, string> | null {
  try {
    const parsed: unknown = JSON.parse(raw);
    if (typeof parsed !== "object" || parsed === null || Array.isArray(parsed))
      return null;
    for (const value of Object.values(parsed)) {
      if (typeof value !== "string") return null;
    }
    return parsed as Record<string, string>;
  } catch {
    return null;
  }
}
```

The port itself. The directory shape collects every `.json` under `Lang/{lang}/` recursively; only when the directory holds no files does it fall back to the single file:

```ts
const overlayPort: I18nPort = {
  async loadOverlayFiles(lang) {
    const dir = `Lang/${lang}`;
    const inDir = (await listFiles(dir, { recursive: true })).filter((p) =>
      p.endsWith(".json"),
    );
    const paths = inDir.length > 0 ? inDir : [`Lang/${lang}.json`];

    const files: I18nOverlayFile[] = [];
    // Merge order decides who wins for the same key, so a deterministic order is required here
    for (const path of paths.sort()) {
      const entries = parseOverlay(await readText(path));
      if (entries === null) continue;
      // path is relative to the overlay root; the single-file shape has no directory prefix and is supplied as main.json
      const rel = path.startsWith(`${dir}/`)
        ? path.slice(dir.length + 1)
        : "main.json";
      files.push({ path: rel, entries });
    }
    return files;
  },

  async listLanguages() {
    const seen = new Set<string>();
    const rest: string[] = [];
    for (const path of await listFiles("Lang")) {
      const lang = path
        .slice(path.lastIndexOf("/") + 1)
        .replace(/\.json(\.enc)?$/, "");
      const key = lang.toLowerCase();
      if (lang === "" || key === "zh-cn" || seen.has(key)) continue;
      seen.add(key); // case-insensitive dedup; keep the first spelling seen
      rest.push(lang);
    }
    return ["zh-CN", ...rest.sort()];
  },
};
```

A few easy mistakes:

- **`path` is relative to the overlay root**, separated by `/`, without the `Lang/{lang}/` level. It takes no part in lookups, but it decides the merge layer — `main.json` is not an arbitrary file name: the engine specifically looks for it first to sit at the bottom. The single-file shape has no directory prefix and is also supplied as `main.json`, so it enjoys the same fallback treatment.
- **Don't hard-code file names.** Hard-coding a concrete path like `chapter1.json` silently breaks the per-story mirror layout; and when the project only has a main table, the unreadable file throws — once `loadOverlayFiles` rejects, `setLanguage` reports `i18n-overlay-failed` and **the whole language switch fails**.
- **Both paths reading nothing** (empty directory, single file absent) takes the same failure path.
- **Enumeration belongs to the supplier.** The two `declare function`s above are illustrative; a real host gives you a resource port or a file source — either works, but don't build `/Lang/...` URLs directly in the page: that bypasses the resource root.

`listLanguages()` is optional; the engine itself never calls it — it is there for your language selector.

The template's host already has this supply wired: the browser and desktop-shell forms both use Web fetch — `Lang/` is a static resource that the desktop shell's WebView can fetch just as well, and the language list comes from a build-time scan of `Resources/Lang/` (`virtual:lang-list`), so adding a language directory requires no list edits. The mini-program form uses the implementation with an injectable HTTP client. The reference host's desktop-shell form uses native supply: it scans `Lang/`, reads files on demand, decrypts ciphertext along the way, and hands the engine finished entries. To wire your own host, use the three ready-made adapters above, or implement the contract following the hand-written example.

## Where the language list comes from

`listLanguages()` exists for your language selector; **the engine itself never calls it** — the engine only knows the language code you pass to `setLanguage("en")`.

The template host does no runtime scanning: the language list is produced at build time by scanning `Resources/Lang/` (the `virtual:lang-list` virtual module, handed to the host through the `src/langs/` exit), and at runtime files are fetched against that list. An empty list means only the default language, with originals shown as-is.

The reference host's native desktop scan recognizes two shapes: a `Lang/{lang}/` directory and a `Lang/{lang}.json` single file. The rules:

- Only **direct children** of `Lang/` count. A nested file like `Lang/en/zh-CN.json` does not become a language.
- The language code is the directory name or the file name (minus `.json` / `.json.enc`).
- Case-insensitive dedup; apart from the default language, sorted by code-point order.
- `zh-CN` is always in the list, first.
- If `Lang/` does not exist or cannot be scanned — return `["zh-CN"]`, no error.

The editor does not use this scan: it collects translation keys as a **cross-language union** (the keys of every `.json` under `Lang/` combined). "This key has no matching original in the story" is independent of any particular language, and looking at a single language would miss dead keys. The trade-off is that the workbench accepts slightly looser language codes than the native scan.

## Switching language

```ts
await engine.setLanguage("en");
```

Passing the empty string returns to the default language (originals shown as-is). A successful switch writes the system key `__current_language`; the host can subscribe to it to update the language marker in its UI. It can also be called before startup, for choosing a language on the title screen:

```ts
await engine.setLanguage("en");
engine.start();
```

When loading fails, the engine keeps the current language and emits `i18n-overlay-failed`:

```text
载入 en 译文 overlay 失败（保持原语言）：Failed to fetch
```

Failure neither stops the story nor falls back to the default language — the previous translation table stays in use. A successful switch **rebuilds the whole table**: the old one is dropped and the new one is reassembled following the merge rules above.

Switching to the same language again is idempotent: if the table hasn't changed, nothing is re-supplied and the UI is not notified again. During rapid consecutive switches the last one wins — an earlier request arriving late will not switch the language back.

## When it takes effect

**State stores originals; translations are derived at the moment of reading.** Dialogue text, speaker names, menu and input prompts and options, the NVL buffer, element text — all of it is stored as originals in the state container, and the display looks them up against the current table when reading. So after a language switch, **the current screen re-translates immediately** — the line being shown, the element text on screen, the lines already scrolled in the NVL all change to the new language, with no need to wait for the next line or re-enter the scene.

Snapshots and saves store originals too:

- Saves no longer contain "the strings as translated at the time". Which language appears after loading depends on **the language setting at load time**: load an English playthrough while the current language is Chinese, and it displays in Chinese.
- Rolling back to any checkpoint derives the history panel and on-screen text in the current language; after a language switch the history lines change too.
- For sentences containing `{variables}`, the object of translation is the **template** (`你好，{name}！`), not the interpolated result; derivation first looks up the template's translation, then inserts the variable values captured at the time. Variable values themselves are never translated.

Older saves stored translations. When such a save is loaded, the engine marks the fields suspected of being translations and skips the lookup for them, avoiding the mistranslation of "translating a translation as if it were the original"; once the story moves on and the engine rewrites those fields, the marks clear. The save format has not changed; no migration tool is needed.

## Which text gets translated

| Location                            | Translated                 |
| ----------------------------------- | -------------------------- |
| `say` text                          | Yes                        |
| `say` speaker name                  | Yes                        |
| `menu` prompt and option labels     | Yes                        |
| `menu` option target column         | **No**                     |
| `input` prompt and option labels    | Yes                        |
| `notify` text                       | Yes                        |
| `character`'s `screen`              | No                         |
| Element `text` property             | Yes (derived at read time) |
| Variable values, expression results | No                         |
| `project.json`'s `name`             | No                         |

Target column names are not translated: they are column ids, not text for players. The `value` of an `input` candidate is likewise untranslated — it is the verbatim value written into a variable; translating it would make story logic drift with the language.

A `character`'s `screen` is the registered name of a dialogue-box template, usually an English identifier like `bubble` — identifiers are not shown to players, so the engine does not translate them; the editor toolchain does include them in the translation checkup's comparison set (see below). A character's display name is `name`, which goes through `say`'s speaker name.

## Originals as-is

With no `i18nPort` wired, or after `setLanguage("")`, the engine does no lookups and sends originals straight out. The `Lang/` directory takes no part at all — nothing is read, and no error is raised.

The default language is declared by `lang` in `Resources/project.json`:

```json
{
  "lang": "zh-CN"
}
```

It is project metadata only; the engine does not auto-load translations based on it — when to load is decided by your `setLanguage()` calls.

## Lookup rules

- A hit uses the translation, **including an empty-string translation** (to hide a line in a given language, write `""`).
- A miss uses the original; no error, and no key is displayed.
- An empty original returns the empty string directly.

So a few missing entries never break the game — those lines simply stay in the original language.

## The host surface: translating UI text

Beyond the story, the host's own UI text — toolbar buttons, save prompts, preference panel titles — should follow the language too. `@lingfan-engine/shell` provides a facade factory:

```ts
import { createHostI18n } from "@lingfan-engine/shell";

const i18n = createHostI18n(engine, { i18nPort });
```

`createHostI18n` is a **factory, not a singleton**: each call builds an independent facade. The first argument takes the engine (`StoryEngine` works directly; a structurally compatible stand-in works too). The second argument is optional: `i18nPort` is only used to ask for the language list — omit it and everything still works, just with only the default language in the list. The facade holds no translation table of its own — lookups, table swaps, and failure handling all live in the engine; the facade merely connects the host to the same supply.

The facade offers:

| Member                | Purpose                                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `t(text)`             | Look up the current table; a hit returns the translation, a miss returns the input unchanged                                      |
| `changeLang(lang)`    | Switch language (via the engine's `setLanguage`); failure keeps the current language                                              |
| `currentLang`         | The current language code, read live from engine state; empty string means the default language                                   |
| `availableLangs`      | Selectable languages, always including the default; filled asynchronously when a port is wired, staying at the default on failure |
| `subscribe(listener)` | Called on language change (receives the new code); returns an unsubscribe function                                                |

The typical wiring: wrap static text in `t()` and re-render on language change —

```ts
const render = () => {
  saveButton.textContent = i18n.t("存档");
  loadButton.textContent = i18n.t("读档");
};
render();
const unsubscribe = i18n.subscribe(render);
```

A few boundaries:

- **The first argument of `t()` must be a literal.** The toolchain collects keys by static scanning: `i18n.t("存档")` enters the key set; a dynamic first argument like `i18n.t(label)` cannot be collected and is listed separately in the scan results as a dynamic call site (first argument not a literal, key cannot be collected statically), with its location. When you need dynamic text, write each possible string as its own literal call.
- **Player-facing text goes through this path**: wrap it in `t()`, put it in the translation table, sharing the same overlay as story content. **Developer-facing diagnostics and debug output do not migrate** — they stay out of the translation table; rewrite them through the host's own text-injection mechanism (such as the notice center's `texts` parameter). Never carry the same sentence through both `t()` and an injection table.
- **Do not wrap story content in `t()` again.** Dialogue, menus, input prompts, element text, NVL, and history lines are already derived by the engine; what the host receives is the translated value. Wrapping it again amounts to looking up a translation as if it were an original.
- UI components such as the notice center and the choices view carry an optional `translate` injection (usually `engine.translate` or the facade's `t`): once injected, the component's built-in player-facing text (like "saved" notices or the input box's confirm button) also goes through the translation table; without injection, behavior is exactly as before.

The template's host is already wired this way: the language selector, toolbar static text, notices, and the choices area all re-render on language switch — see `src/host/i18n.ts` for a working reference.

## Encrypted translations

In projects with resource encryption, translation files carry the `.enc` suffix too:

```text
Resources/Lang/en/main.json.enc
```

The engine knows nothing about this. `loadOverlayFiles` hands it "path + entries", with no plaintext/ciphertext field — `Lang/en/main.json` and `Lang/en/main.json.enc` are the same thing to it. Decryption happens on the supply side, under the same arrangement as resources and saves; see [Encryption and Platform Supply](/concepts/encryption/).

For the supplier to decrypt, the project must first declare `resourceEncryption` in `project.json`:

- With `resourceEncryption: true` declared, ciphertext decrypts normally and the resulting entries merge as usual.
- Ciphertext appearing without the declaration fails the whole load — `setLanguage()` reports `i18n-overlay-failed` and keeps the current language.

The browser-form editor reads back the ciphertext itself, so JSON parsing necessarily fails and that file is skipped. This is deliberate under-reporting rather than false alarms: the editor would rather say nothing than report a pile of missing translations that aren't actually missing.

## The localization workbench in the editor

The "Localization" panel in the editor's right column manages `Lang/**`. Start it:

```bash
pnpm editor
```

It opens at http://localhost:1425 by default. The panel header shows the number of originals, with one row per language below.

You must "open a project" first — the panel's data comes from the translation keys scanned in the opened project. When the project has no `Lang/` files yet, it shows an empty state ("no languages created yet"), not an error. It never touches disk on its own: writes go through the editor's save channel, and nothing you click in the panel lands on disk behind your back.

### How coverage is computed

Each row shows three things: a **character-weighted percentage** (the most prominent), a status label, and `translated/total`. Hovering the percentage reveals the full picture:

```text
按字数加权 62%（长句权重更大）· 按条数 88% · 原文 1240 字
```

The two numbers differ because a per-entry ratio treats a long line of dialogue and a two-character word alike. Translators feel untranslated long lines more acutely, so the main display is character-weighted. Weights use the **original's length**, not the translation's — weighting by translation length would reward "translating verbosely".

Each language also carries a status label:

| Label                | Meaning                                 |
| -------------------- | --------------------------------------- |
| Not started          | Nothing translated yet                  |
| Partial              | Some entries translated                 |
| Fully translated     | Every original has a translation        |
| Nothing to translate | No originals extracted from the project |

"Nothing to translate" is an explicitly detected empty state: the percentage slot shows "—", not `NaN%` and not a satisfying-looking 100% — either of the latter would make you think the translation is done.

When entries are missing, the row grows a "missing" button opening a list, each item followed by a "translate" jump into that language's table. Keys present in translation tables but absent from the originals are summarized at the bottom of the workbench as the total number of orphaned entries across languages.

### Creating a language

At the bottom, enter a language code (`en`, `zh-CN`, …), pick a layout, and click "generate skeleton". The three dropdown items match the table above:

```text
按主表（Lang/{lang}/main.json）
单文件（Lang/{lang}.json）
按故事镜像
```

The first is selected by default. What gets generated is a **translation table skeleton**: every original in the project becomes a key, with placeholder values. The per-story mirror copies the directory structure of `Stories/`, one file per story.

There are two placeholder strategies. The default is **original-as-placeholder** — the screen stays readable before translation, which suits a translation worksheet. The other is empty-string placeholder: the key exists with value `""`, which hides the line at runtime once hit — for when you want untranslated content simply not to show. The editor panel uses the default original placeholder.

Generation is **incremental**: existing translations for that language are preserved as-is (including empty strings you left deliberately); only new keys are added. If the language already exists, it asks first: "Generate the skeleton anyway? Existing translations are preserved (incremental mode), but same-named files may be overwritten."

The language code must be a single safe file-name segment — it becomes a directory name, under the same rules as story file names. Anything with `/`, written as `..`, or starting with a dot is rejected:

```text
语言码不合法：../x（须为单段安全文件名）
```

After generation it reports the file count, then re-enumerates the project so the diagnostics panel and workbench numbers update. A write error mid-way pops a failure notice — but files already written are not rolled back; check which ones landed.

### Editing a translation table

Click a language code (or a "translate" jump from the missing list) to enter the table: keys on the left, values on the right; rows can be added, removed, and edited.

- **Typing stages changes; saving is explicit.** Nothing is written to disk while you type.
- Empty translations show a gray "untranslated" placeholder rather than blank space — blank cannot distinguish "not yet translated" from "deliberately empty", and those two behave completely differently at runtime.
- Adding a row asks for the key first: the key must match the original verbatim, because runtime lookups use it.
- Deleting a row asks for confirmation, because deletion is final — translation tables carry no backup.

## The translation checkup

Several translation-related diagnostics in the editor's diagnostics panel, all at warning level:

**Unused translation key.** The table has this key, but no matching original exists in the project:

```text
未使用的译文键：你好（say / menu / input / notify 四个翻译面均未命中原文——该键运行期不会生效；若这段文字只用于元素文本或宿主界面，本条可忽略）
```

The four command surfaces named in the message are shorthand: the comparison actually covers five command surfaces (`say` text and speaker, `menu`, `input`, `notify`, `character`'s `screen`), plus element `text` and the static-text keys wrapped in `t()` in host source. A hit usually means a line was reworded without updating the translation table.

**Missing translation.** An original is not hit by any language's overlay:

```text
原文未有任何译文：欢迎回来（所有语言的 overlay 均未命中——运行期回退原文；专有名词等有意保留原文的可忽略）
```

This one only fires when the project **actually has** overlay keys. A purely Chinese project is not flooded by it.

**Unmarked host text.** Host source contains literals with Chinese text that are not wrapped in `t()` — they never enter the key set and will never be translated. The diagnostic lists each with file, line, and column, reminding you to wrap player-facing text; pure comments and literals without Chinese are not reported.

**Layout conflict.** Under one language, the same key appears in several files with different values. Merging is last-write-wins, so a conflict means one translation is silently shadowed — the diagnostic lists the conflicting keys and files, and you decide which to keep.

Homogeneous diagnostics drown heterogeneous ones — two real errors buried in thirty-odd "unused translation key" warnings are hard to spot. So the diagnostics panel groups by kind: the error group always sits on top, never collapsed; warning groups with more than one item collapse by default. The orphan total at the bottom of the workbench and the "unused translation key" diagnostics are the same data.
